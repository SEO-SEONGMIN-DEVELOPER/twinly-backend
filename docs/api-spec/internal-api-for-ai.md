# Internal API 연동 가이드 (AI 서버용)

AI 서버가 호출하는 백엔드 내부 API 3종의 계약 문서입니다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/internal/v1/users` | 시뮬레이션 대상 유저 ID 목록 조회 (신규 유저 발견용) |
| POST | `/internal/v1/users/{userId}/simulations` | 하루치 시뮬레이션 결과(장면·질문·관계) 저장 |
| GET | `/internal/v1/users/{userId}/persona` | 시뮬레이션 입력용 유저 페르소나 조회 |

배치 1회의 기본 흐름은 다음과 같습니다.

```
1. GET /internal/v1/users?cursor={마지막으로 받은 userId}   → 신규 유저를 자기 DB에 등록
2. 유저별로 GET .../persona                                → 최신 페르소나 확보 (404면 파기된 유저)
3. 유저별로 POST .../simulations                           → 하루치 결과 저장
```

베이스 URL은 환경별로 별도 공유합니다.

## 0. 공통 규칙

### 인증

`/internal/v1/**` 은 **애플리케이션 레벨 인증이 없습니다.** 토큰·헤더 없이 호출합니다.
보호는 전적으로 네트워크 경계(보안그룹/VPC)에 의존하므로, 이 경로는 외부에 노출되면 안 됩니다.

### 숫자 ID는 전부 문자열

`userId`, `partnerId` 등 모든 숫자 ID는 **요청·응답 모두 문자열**로 주고받습니다.

```json
{ "userId": "12" }
```

JS/JSON 파서의 정수 정밀도 문제를 피하기 위한 규칙입니다. 파이썬에서 보낼 때도 `str(user_id)` 로 감싸주세요.

### 날짜·시간 포맷

| 필드 | 포맷 | 예시 |
|---|---|---|
| `date` | `YYYY-MM-DD` | `"2026-08-11"` |
| `start`, `end`, `occursAt`, `time`, `updateTime` | `YYYY-MM-DDTHH:mm:ss` | `"2026-08-11T09:30:00"` |

타임존 개념이 없는 로컬 날짜/시간입니다. 서버는 받은 값을 그대로 저장하므로, **AI 쪽에서 KST 기준으로 맞춰서 보내야 합니다.**

**오프셋을 붙이면 안 됩니다.** `"2026-08-11T09:30:00+09:00"` 처럼 보내면 파싱에 실패해 400입니다. 초는 생략할 수 있습니다(`"2026-08-11T09:30"`).

### `date` 는 달력 날짜가 아니라 하루 회차입니다

`date` 는 **이 데이터가 어느 하루 묶음에 속하는지**를 나타내는 키입니다. 각 시각의 날짜와 달라도 되고, 서버는 둘의 일치 여부를 검증하지 않습니다.

하루를 `06:00 ~ 다음 날 04:00` 으로 잡으신다면, `date: "2026-08-11"` 회차 안에 이런 값이 들어갑니다.

```json
{ "start": "2026-08-11T09:00:00", ... }   // 그 날 낮
{ "start": "2026-08-12T01:30:00", ... }   // 자정을 넘긴 새벽 — date 는 그대로 08-11
```

`date` 는 재전송 시 교체 단위이자 조회 단위입니다. **한 회차의 데이터는 시각이 며칠에 걸치든 같은 `date` 로 보내주세요.** 새벽 부분만 다음 날짜로 보내면 그 부분이 다른 회차에 섞여 재전송 시 유실됩니다.

### 에러 응답 형식

모든 에러는 아래 형태로 통일됩니다. HTTP 상태 코드는 에러 코드에 따라 달라집니다.

```json
{
  "code": "USER_NOT_FOUND",
  "message": "존재하지 않는 유저입니다."
}
```

**`message`는 고정 문구입니다.** 어떤 필드가 왜 틀렸는지는 내려주지 않으니, 분기는 반드시 `code` 로 하세요. 로그에 남길 때도 `code` 기준으로 집계하시면 됩니다.

## 1. POST /internal/v1/users/{userId}/simulations

하루치 시뮬레이션 결과를 저장합니다.

### Path Parameter

| 이름 | 타입 | 설명 |
|---|---|---|
| `userId` | string(숫자) | 대상 유저 ID. 숫자로 변환할 수 없으면 400 |

### Request Body

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `userId` | string(숫자) | O | **path의 `userId`와 반드시 같아야 합니다.** 다르면 400 |
| `date` | string(`YYYY-MM-DD`) | O | 시뮬레이션 대상 회차. 위 "하루 회차" 규칙 참고 |
| `scenes` | array | O | 장면 목록. 빈 배열 허용 |
| `questions` | array | O | 질문 목록. 빈 배열 허용 |
| `relationships` | array | O | 관계 갱신 목록. 빈 배열 허용 |

`scenes` / `questions` / `relationships` 는 **null 불가**입니다. 없으면 `[]` 로 보내주세요.

### scenes[] — `type` 으로 갈리는 두 종류

`type` 값에 따라 필드 구성이 달라집니다. **`type` 값은 대소문자를 구분합니다** (`"action"`, `"dialogue"` 소문자 고정).

#### type = "action" (행동 장면)

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `type` | `"action"` | O | 판별자 |
| `start` | time | O | 시작 시각 |
| `end` | time | O | 종료 시각 |
| `place` | string | O | 장소. 공백 문자열 불가 |
| `with` | string(숫자)[] | X | 동행 유저 ID 목록. 생략/null 가능, 중복은 서버가 제거 |
| `narration` | string | O | 장면 서술. 공백 문자열 불가 |
| `mind` | string | X | 속마음. 생략/null 가능 |

#### type = "dialogue" (대화 장면)

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `type` | `"dialogue"` | O | 판별자 |
| `start` | time | O | 시작 시각 |
| `end` | time | O | 종료 시각 |
| `place` | string | O | 장소. 공백 문자열 불가 |
| `with` | string(숫자)[] | **O** | 대화 상대 유저 ID 목록. **빈 배열 불가(최소 1명)**, 중복은 서버가 제거 |
| `lines` | array | O | 대사 목록. null 불가 |

**`with`은 action 장면과 달리 필수입니다.** 혼자 등교하는 행동 장면은 동행이 없을 수 있지만, 상대 없는 대화 장면은 성립하지 않기 때문입니다. `null`이나 `[]` 로 보내면 400입니다.

### lines[] — `t` 로 갈리는 두 종류

**주의: `t` 는 시간이 아니라 라인 종류 판별자입니다.** `"narr"` 또는 `"bubble"` 소문자 고정입니다.

#### t = "narr" (지문)

| 필드 | 타입 | 필수 |
|---|---|---|
| `t` | `"narr"` | O |
| `text` | string | O (공백 불가) |
| `occursAt` | time | O |

#### t = "bubble" (말풍선)

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `t` | `"bubble"` | O | 판별자 |
| `userId` | string(숫자) | O | **말한 사람**의 유저 ID |
| `action` | string | X | 말할 때의 행동/표정. 생략/null 가능 |
| `text` | string | O | 대사. 공백 불가 |
| `occursAt` | time | O | 이 대사가 나온 시각 |

`action` 은 선택입니다. 묘사할 행동이 없으면 필드를 빼거나 `null` 로 보내주세요. 서버는 받은 값을 그대로 저장하고 조회 API 에서도 `"action": null` 로 내려갑니다.

#### `occursAt` (두 종류 공통)

라인 하나하나가 언제 일어났는지를 나타내는 시각입니다. **`narr`·`bubble` 모두 필수**이며, 누락하면 400입니다.

- 장면의 `start` / `end` 와 같은 날짜 포함 로컬 시각입니다. **AI 쪽에서 KST 기준으로 보내주세요.**
- **서버는 `start ≤ occursAt ≤ end` 를 검증하지 않고, 라인 간 순서도 검증하지 않습니다.** 범위를 벗어나거나 뒤로 가는 값도 그대로 저장되니, 정합성은 AI 쪽에서 보장해야 합니다.
- 유저에게 내려갈 때는 받은 값에 KST 오프셋만 붙여 절대시각(예: `"2026-08-11T12:15:00+09:00"`)으로 변환됩니다. `start` / `end` 와 동일한 규칙입니다.

### questions[]

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `time` | time | O | 질문이 뜨는 시각 |
| `qtype` | `"promise"` \| `"persona"` | O | 질문 종류 |
| `partnerId` | string(숫자)[] | **O** | 관련 상대 유저 ID 목록. **빈 배열 불가(최소 1명)** |
| `text` | string | O | 질문 내용. 공백 불가 |
| `options` | string[] | O | 선택지. null 불가, 빈 배열은 허용 |

`qtype` 은 대소문자를 가리지 않지만(`accept-case-insensitive-enums`), **소문자로 통일해서 보내주세요.**

### relationships[]

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `partnerId` | string(숫자) | O | 상대 유저 ID |
| `updateTime` | time | O | 관계가 갱신된 시각 |
| `rapport` | int | O | 친밀도. 아래 임계값 참고 |
| `partnerModel` | string | O | 요청의 `userId` 유저가 이 상대에 대해 파악한 정보. 공백 불가 |

#### partnerModel

`userId` 유저의 시점에서 본 상대 유저의 상(像)입니다. 시뮬레이션 결과 그 유저가 상대에 대해 알게 된 성격·취향·관계 맥락 등을 자연어로 담아 보내주세요.

- **시점이 중요합니다.** 같은 두 사람이라도 A→B 와 B→A 의 `partnerModel` 은 서로 다릅니다. 항상 요청의 `userId` 가 주체입니다.
- 서버는 내용을 해석하지 않고 문자열 그대로 저장하며, 조회 시 해당 상대에 대한 **가장 최신 기록**을 그대로 내려줍니다. 따라서 매번 이전 내용을 포함한 **누적된 전체 상**을 보내주세요. 직전 회차와의 차이분만 보내면 이전 정보가 사라집니다.

#### rapport 임계값 (중요)

| 범위 | 관계 | 부수 효과 |
|---|---|---|
| ~29 | 지인(acquaintance) | 없음 |
| 30~69 | 친구(friend) | 지인→친구 전환 시 **친구 알림 발송** |
| 70~ | 절친(bestFriend) | 위 + **채팅방 자동 개설 + 매칭 알림 발송** |

**서버는 rapport 범위를 검증하지 않습니다.** 음수나 1000을 보내도 그대로 저장되고 임계값 로직만 적용됩니다. 0~100 범위 보장은 AI 쪽 책임입니다.

### Response

**200 OK, 응답 본문 없음.**

성공 여부는 상태 코드로만 판단하시면 됩니다. 저장된 버전 번호 등은 응답에 포함되지 않습니다.

### 에러 응답

| HTTP | code | 발생 조건 |
|---|---|---|
| 400 | `INVALID_REQUEST` | path `userId`가 숫자가 아님 / body `userId` ≠ path `userId` / 필수 필드 누락·공백 / dialogue `with`·question `partnerId`가 비어 있음 / `type`·`t` 판별자 값 오류 / `qtype` 값 오류 / 날짜·시간 포맷 오류(오프셋 포함 시) / JSON 파싱 실패 |
| 404 | `USER_NOT_FOUND` | 해당 유저가 존재하지 않음 |
| 405 | `METHOD_NOT_ALLOWED` | 메서드 오류 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | `Content-Type: application/json` 누락 |
| 500 | `INTERNAL_ERROR` | 서버 오류 |

400은 전부 `INVALID_REQUEST` 하나로 뭉뚱그려집니다. **어떤 필드가 틀렸는지 응답으로는 알 수 없으니**, 개발 중에는 요청 본문을 로그로 남겨두시는 편이 디버깅에 유리합니다.

## 2. GET /internal/v1/users/{userId}/persona

시뮬레이션 입력으로 쓸 유저 페르소나를 조회합니다.

### Path Parameter

| 이름 | 타입 | 설명 |
|---|---|---|
| `userId` | string(숫자) | 대상 유저 ID. 숫자로 변환할 수 없으면 400 |

### Response (200 OK)

| 필드 | 타입 | null 가능 | 설명 |
|---|---|---|---|
| `userId` | string(숫자) | X | 유저 ID |
| `familyName` | string | X | 성 |
| `givenName` | string | X | 이름 |
| `gender` | `"male"` \| `"female"` | X | 성별 |
| `school` | string | X | 학교 |
| `affiliation` | string | X | 소속(학과 등) |
| `birthDate` | string(`YYYY-MM-DD`) | X | 생년월일 |
| `personaElements` | object | X | 차원별 성향 목록. 아래 참고 |

```json
{
  "userId": "12",
  "familyName": "서",
  "givenName": "성민",
  "gender": "male",
  "school": "성균관대학교",
  "affiliation": "컴퓨터공학과",
  "birthDate": "1999-03-21",
  "personaElements": {
    "openness": ["새로운 시도를 즐긴다"],
    "conflictStyle": ["직접 말하기보다 시간을 둔다"],
    "interest": ["등산", "재즈"],
    "detail": ["요즘 가장 자주 하는 생각이 뭐예요?: 졸업하고 뭐 할지 고민이에요"]
  }
}
```

**`personaElements` 를 제외한 모든 필드는 항상 값이 있습니다.** 회원가입 시점에 이름·성별·학교·소속·생년월일이 전부 필수로 검증되므로(`PROFILE_NOT_COMPLETED`), 가입이 완료된 유저에게 이 값들이 비어 있는 경우는 없습니다. null 체크 없이 바로 쓰셔도 됩니다.

### personaElements 규칙 (중요)

**값이 존재하는 차원만 키로 포함됩니다.** 요소가 하나도 없는 차원은 빈 배열이 아니라 **키 자체가 없습니다.** 전부 비어 있으면 `{}` 입니다.

```python
# 이렇게 접근하면 KeyError
elements["interest"]

# 이렇게 접근하세요
elements.get("interest", [])
```

가능한 키 (총 10종):

| 키 | 설명 |
|---|---|
| `openness` | 개방성 |
| `conscientiousness` | 성실성 |
| `extraversion` | 외향성 |
| `agreeableness` | 우호성 |
| `neuroticism` | 신경성 |
| `lifeStyle` | 생활 양식 |
| `conflictStyle` | 갈등 대처 방식 |
| `communicationStyle` | 의사소통 방식 |
| `interest` | 관심사 |
| `detail` | **온보딩 AI 대화 원문** |

#### `detail` 은 성격이 다릅니다

나머지 9개는 설문 응답에서 매핑된 **짧고 정제된 성향 문장**입니다. 반면 `detail` 은 온보딩 AI 채팅에서 유저가 직접 친 답변을 `"질문: 답변"` 형식으로 그대로 저장한 것이며, **대화 턴 수만큼 누적됩니다.**

따라서 `detail` 은 응답에서 가장 부피가 큰 필드가 되기 쉽습니다. 프롬프트에 그대로 넣으실 거라면 토큰 예산을 따로 잡아두세요.

### 에러 응답

| HTTP | code | 발생 조건 |
|---|---|---|
| 400 | `INVALID_REQUEST` | `userId`가 숫자가 아님 |
| 404 | `USER_NOT_FOUND` | 유저가 없거나 **탈퇴한 유저** |
| 500 | `INTERNAL_ERROR` | 서버 오류 |

## 3. GET /internal/v1/users

시뮬레이션 대상 유저 ID 목록을 오름차순으로 조회합니다. **신규 가입자를 발견하는 유일한 경로입니다.**

### Query Parameter

| 이름 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| `cursor` | string(숫자) | X | 없음(처음부터) | 이 값보다 **큰** userId만 반환 |
| `limit` | int | X | `500` | 1~500. 범위를 벗어나면 400 |

### Response (200 OK)

```json
{
  "userIds": ["13", "14", "15"],
  "page": {
    "nextCursor": "15",
    "hasMore": true
  }
}
```

| 필드 | 타입 | null 가능 | 설명 |
|---|---|---|---|
| `userIds` | string(숫자)[] | X | userId 오름차순. 없으면 `[]` |
| `page.nextCursor` | string(숫자) | O | 다음 호출에 넘길 커서. `hasMore`가 `false`면 `null` |
| `page.hasMore` | boolean | X | 더 받을 게 남았는지 |

### 사용법

AI 서버가 **자기 DB에 가진 가장 큰 userId**를 `cursor`로 넘기고, `hasMore`가 `false`가 될 때까지 `nextCursor`로 반복 호출합니다.

```python
cursor = my_db.max_user_id()   # 없으면 None
while True:
    res = get("/internal/v1/users", params={"cursor": cursor} if cursor else {})
    my_db.register(res["userIds"])
    if not res["page"]["hasMore"]:
        break
    cursor = res["page"]["nextCursor"]
```

`cursor`를 생략하면 처음부터 전부 내려오므로, 최초 1회는 생략하고 이후부터 커서를 쓰시면 됩니다.

### 커서가 날짜가 아니라 userId인 이유

`userId`는 auto increment라 단조 증가가 보장됩니다. 가진 것 중 최대값 기준으로 자르면 **누락도 중복도 없습니다.**

가입 시각 기준으로 잘랐다면 커밋 순서와 시각 순서가 어긋나는 경계에서 유실이 생길 수 있는데, ID 커서는 그 문제가 없습니다. 재시도해도 결과가 같으니 배치가 실패하면 그냥 다시 부르시면 됩니다.

### 목록에서 빠지는 유저

파기가 완료된 유저(아래 4-5 참고)는 목록에서 제외됩니다. 이미 받아간 유저가 이후에 파기되면 목록에서는 조용히 사라지므로, **파기 감지는 이 API가 아니라 persona 조회 404로 하셔야 합니다.**

### 에러 응답

| HTTP | code | 발생 조건 |
|---|---|---|
| 400 | `INVALID_REQUEST` | `cursor`가 숫자가 아님 / `limit`이 1~500 범위 밖 |
| 500 | `INTERNAL_ERROR` | 서버 오류 |

## 4. 꼭 알아야 할 동작

### 4-1. 같은 `(userId, date)` 재전송은 전체 교체입니다

같은 유저·같은 날짜로 다시 POST하면, **기존 그 날짜의 scenes·questions·relationships를 전부 삭제하고 새로 저장합니다.** 내부 version이 `v1 → v2` 로 올라갑니다.

- 중복 데이터가 쌓이지 않으므로 **네트워크 오류 시 재시도해도 안전합니다.**
- 다만 **유저가 이미 답변한 질문의 응답(선택지, 답변 시각)도 함께 삭제됩니다.** 하루가 진행되는 도중에 같은 날짜로 재전송하면 유저 답변이 유실됩니다. 재전송은 유저가 아직 해당 날짜를 소비하기 전에만 하시는 게 안전합니다.

### 4-2. 부분 저장은 없습니다

요청 전체가 하나의 트랜잭션입니다. 장면 10개 중 1개가 검증에 걸리면 **10개 모두 저장되지 않습니다.** 400을 받으면 "아무것도 안 들어갔다"고 간주하시면 됩니다.

단, 채팅방 개설만은 별도 트랜잭션으로 처리됩니다. 드물게 본 저장이 실패해도 채팅방은 남을 수 있습니다.

### 4-3. relationships는 유저에게 보이는 알림을 발생시킵니다

`relationships` 전송은 단순 저장이 아니라 **유저 앱에 푸시/알림이 나가는 트리거**입니다.

- `rapport ≥ 70` → 채팅방 자동 개설 + "채팅방이 열렸어요" 알림
- 이전 관계가 지인이었다가 `rapport ≥ 30` 이 되면 → "친구가 되었어요" 알림

친구 판정은 **해당 `date` 이전의 가장 최근 관계 기록**과 비교합니다. 테스트 데이터를 실 계정에 쏘면 실제 알림이 나가니 주의하세요.

### 4-4. 탈퇴 유저는 보내지 않아야 합니다

POST simulations는 유저 존재 여부만 확인하고 **탈퇴 여부는 검사하지 않습니다.** 탈퇴 유저로 요청해도 200이 떨어지고 데이터가 그대로 저장됩니다.

반면 GET persona는 파기된 유저에 404를 반환합니다. 따라서 **persona 조회를 먼저 하고, 404면 해당 유저의 POST를 생략하는 순서**로 태워주세요. 이 순서가 탈퇴 유저를 거르는 유일한 장치입니다.

### 4-5. 탈퇴는 persona 404로 감지합니다

백엔드의 탈퇴 처리는 두 단계입니다.

| 시점 | 백엔드 | persona 조회 | 신규 유저 목록 |
|---|---|---|---|
| 탈퇴 요청 | 복구 가능 상태로 표시 | **200 정상** | 포함됨 |
| 이후 15일간 | 유저가 복구하면 없던 일이 됨 | **200 정상** | 포함됨 |
| 유예 종료 후 매일 04:00 KST 배치 | 개인정보 파기 확정 | **404** | 제외됨 |

즉 **404는 "복구 불가능한 파기가 확정됐다"는 신호**입니다. 되살아날 일이 없으므로, 404를 받으면 **AI 서버 DB에서도 해당 유저 데이터를 파기**하시면 됩니다. 별도의 탈퇴 통보 API나 웹훅은 없습니다.

이 방식이 성립하려면 한 가지만 지키면 됩니다.

**persona를 캐싱하지 말고 매일 조회할 것.** 백엔드가 페르소나를 갱신하므로 어차피 매일 받아야 하고, 404 감지도 여기에 얹힙니다.

**배치를 언제 돌리든 상관없습니다.** 파기 배치가 04:00 KST에 돌긴 하지만, 404는 그 순간에만 오는 이벤트가 아니라 **한 번 파기되면 계속 유지되는 상태**입니다. 04:00 직전에 배치를 돌려 그날 못 잡았더라도 다음 배치에서 그대로 404가 나오므로, 신호를 놓칠 일이 없습니다. AI 서버 배치 시각은 자유롭게 정하시면 됩니다.

참고로 **탈퇴 요청 후 유예 기간에는 persona가 정상 응답하므로 시뮬레이션이 계속 생성됩니다.** 유저가 그 사이 복구할 수 있기 때문에 의도된 동작입니다.

한 가지 더, 백엔드는 파기 시 그 유저의 과거 장면·관계 기록을 지우지 않고 **이름만 `"탈퇴한 사용자"` 로 대체**합니다. 상대 유저의 기록에서 그 사람만 통째로 사라지면 부자연스럽기 때문입니다. AI 서버도 같은 정책(기록은 남기되 식별정보만 익명화)을 따르시면 양쪽이 일관됩니다.

### 4-6. 404 재시도는 의미 없습니다

`USER_NOT_FOUND` 는 유저가 없거나 파기된 상태이므로 재시도해도 결과가 같습니다. 재시도 대상은 5xx와 네트워크 오류로 한정하시고, 400/404는 즉시 실패 처리 후 로그로 남기시면 됩니다.
