# WebSocket 클라이언트 구현 가이드 (프론트엔드용)

이 문서는 **WebSocket 연결의 생명주기**(연결 수립 → 유지 → 끊김 → 재연결 → 복구)를 프론트엔드가 어떻게 다뤄야 하는지를 담습니다.

각 이벤트의 페이로드 스키마는 **AsyncAPI 스펙(springwolf)** 이 원천이며, 이 문서는 그 위에서 **"언제 무엇을 해야 하는가"** 를 정의합니다.

> 원천(SSOT): 백엔드 `common.websocket` 패키지 및 `connection` 패키지. 코드가 바뀌면 이 문서도 갱신해야 합니다.

---

## 0. 배경: 왜 지금 이 문서가 필요한가

백엔드를 **서버 1대 → 여러 대(다중 인스턴스)** 로 확장할 예정입니다.

**계약(주소·데이터 형식)은 하나도 바뀌지 않습니다.** 서버끼리 메시지를 주고받는 방식이 달라질 뿐이고, 그건 프론트에서 보이지 않습니다.

대신 딱 하나가 바뀝니다.

> **연결이 끊기는 빈도가 크게 늘어납니다.**

서버가 1대일 땐 배포할 때 1번 끊겼습니다. 서버가 3대가 되면 서비스를 멈추지 않기 위해 **한 대씩 순서대로** 교체하므로, 배포 한 번에 **3번** 끊깁니다. 여기에 트래픽에 따라 서버 대수를 자동 조절하는 설정까지 들어가면 더 잦아집니다.

즉 **끊김이 "예외 상황"에서 "정상 동작의 일부"로 바뀝니다.** 아래 항목들은 전부 여기서 나옵니다.

## 1. 요약 체크리스트

먼저 현재 구현 상태부터 확인해 주세요. 이미 되어 있는 항목은 넘어가시면 됩니다.

| # | 항목 | 없으면 생기는 일 | 상세 |
|---|---|---|---|
| 1 | 재연결 시 **티켓을 매번 새로 발급** | 재연결이 항상 401로 실패 | [3장](#3-연결-수립-절차) |

| 4 | 재연결 직후 **REST 재조회** | 끊겨 있던 동안의 메시지가 **영영 안 보임** | [7장](#7-재연결-후-데이터-복구-필수) |

| 6 | STOMP **heartbeat 헤더 설정** | 조용한 대화방에서 60초마다 끊김 | [9장](#9-heartbeat-설정) |

**4번(재연결 후 재조회)이 가장 중요합니다.** 이게 없으면 데이터 유실이 사용자에게 그대로 노출됩니다.

## 2. 바뀌지 않는 것

혼란을 줄이기 위해 먼저 못 박아둡니다. 아래는 서버 확장과 **무관하게 그대로**입니다.

- WebSocket 접속 주소 (`/ws/v1/`)
- 티켓 발급 API (`POST /api/v1/connection-tokens`)
- 모든 구독 주소 (`/user/queue/...`)
- 모든 메시지 봉투와 페이로드 스키마
- 모든 REST API

## 3. 연결 수립 절차

WebSocket 연결은 **2단계**입니다. 액세스 토큰으로 바로 접속하는 게 아니라, 일회용 티켓을 먼저 받습니다.

### 3-1. 티켓 발급

```http
POST /api/v1/connection-tokens
Authorization: Bearer {accessToken}
Content-Type: application/json

{ "connectionType": "WS" }
```

**응답**

```json
{
  "ticket": "3f9a1c2e-...-8b7d",
  "connectionType": "WS",
  "expiresAt": "2026-07-28T14:04:11+09:00"
}
```

> ⚠️ `connectionType`은 **대문자 `"WS"`** 입니다. `"ws"`로 보내면 400 `INVALID_REQUEST`가 떨어집니다.

### 3-2. 핸드셰이크

발급받은 티켓을 **쿼리 파라미터**로 붙여 접속합니다.

```
wss://{host}/ws/v1/?ticket={ticket}
```

> ⚠️ 경로 끝의 **슬래시(`/`)가 있어야 합니다.** `/ws/v1?ticket=...`은 동작하지 않습니다.

**핸드셰이크 실패 응답**

| 상태 | 의미 | 대응 |
|---|---|---|
| `401` | 티켓이 없거나 / 형식이 잘못됐거나 / 만료됐거나 / **이미 사용됨** | 티켓을 새로 발급받아 재시도 |
| `403` | `connectionType` 불일치 (예: SSE용 티켓으로 WS 접속) | 요청 body의 `connectionType` 확인 (버그) |

### 3-3. 티켓 규칙 — 반드시 지켜야 합니다

| 규칙 | 값 |
|---|---|
| 유효 기간 | **60초** |
| 사용 횟수 | **1회** (핸드셰이크 시점에 소모됨) |

여기서 나오는 두 가지 절대 규칙입니다.

**① 연결 시도 1회 = 티켓 발급 1회**
재연결이든 최초 연결이든, 접속을 시도할 때마다 티켓을 새로 받아야 합니다. 이전 티켓 재사용은 **무조건 401**입니다.

**② "미리 받아두기" 금지**
반드시 **티켓 발급 → 곧바로 접속** 순서여야 합니다.

특히 5장의 백오프 대기 시간이 60초를 넘어가는 경우, 대기 전에 받아둔 티켓은 이미 만료된 상태입니다. **대기 → 티켓 발급 → 접속** 순서를 지켜주세요.

```ts
// ❌ 잘못된 순서 — 대기 중에 티켓이 만료됨
const { ticket } = await issueTicket();
await sleep(backoffMs);
connect(ticket);

// ✅ 올바른 순서
await sleep(backoffMs);
const { ticket } = await issueTicket();
connect(ticket);
```

**③ 티켓 발급이 401이면 재연결 루프를 멈춥니다**
이건 소켓 문제가 아니라 로그인 세션이 만료된 것입니다. 액세스 토큰을 갱신한 뒤 재연결을 다시 시작해야 합니다. 그대로 재시도하면 무한 실패합니다.

## 4. 구독 주소와 메시지 봉투

### 4-1. 구독 주소

연결 직후 아래 주소들을 구독합니다.

| 주소 | 용도 |
|---|---|
| `/user/queue/chat/index` | 채팅방 목록 갱신 신호 |
| `/user/queue/chat/rooms/{roomId}` | 특정 방의 새 메시지, 상대의 읽음 위치 이동 |
| `/user/queue/chat/commands` | 내가 보낸 커맨드의 처리 결과 |
| `/user/queue/connection/control` | **연결 제어 신호 (6장)** |

> `/user` 접두사는 "나에게만 오는 메시지"라는 뜻입니다. 서버가 내부적으로 세션별 주소로 변환하므로, 구독할 때 유저 ID를 넣을 필요가 없습니다.

### 4-2. 공통 봉투

모든 수신 메시지는 아래 형태를 공유합니다.

```ts
{
  v: 1,                    // 스키마 버전
  kind: string,            // "event" | "control" | "command-result"
  type: string,            // 예: "chat.message.created"
  payload: object,         // kind/type에 따라 달라짐
  // ...kind별 추가 필드
}
```

| `kind` | 의미 | 추가 필드 |
|---|---|---|
| `event` | 서버에서 발생한 사건 알림 | `eventId`, `occurredAt` |
| `command-result` | 내가 보낸 커맨드의 결과 | `commandId`, `occurredAt` |
| `control` | **연결 자체에 대한 제어 신호** | 없음 |

**분기는 `type`으로 하시고, `kind`는 큰 분류로만 쓰세요.**

### 4-3. 숫자 ID는 문자열로 내려갑니다

`messageId`, `roomId` 등의 ID는 JSON에서 **문자열**입니다.

```json
{ "roomId": "1024", "message": { "messageId": "88123", ... } }
```

JavaScript의 `number`가 큰 정수를 정확히 표현하지 못하는 문제를 피하기 위한 것입니다. **문자열 그대로 다루시고, `Number()`로 변환하지 마세요.** 비교도 문자열 비교로 하시면 됩니다.

## 5. 재연결 정책

### 5-1. 왜 랜덤 지연이 필요한가

지수 백오프만으로는 부족합니다. 이유를 정확히 이해하고 넘어가 주세요.

서버 A가 죽으면, **거기 붙어 있던 클라이언트 전부가 동시에** 끊깁니다. 이들이 모두 같은 백오프 규칙을 따르면 **정확히 같은 순간에** 재연결을 시도합니다. 그 부하가 살아남은 서버 B, C에 한꺼번에 쏟아지고, B가 그 부하로 넘어가면 B의 클라이언트까지 합류해 C로 몰립니다.

**서버 1대의 장애가 전체 장애로 번집니다.**

이걸 막으려면 재연결 시점이 **클라이언트마다 흩어져야** 합니다. 그래서 대기 시간에 랜덤 값을 섞습니다.

### 5-2. 권장 구현

```ts
const BASE_MS = 1_000;
const MAX_MS = 30_000;

/** 재연결까지 대기할 시간(ms) */
function backoffMs(attempt: number, retryAfterMs?: number | null): number {
  // 서버가 대기 시간을 지정했으면 그 값을 기준으로 삼는다
  const base = retryAfterMs ?? Math.min(MAX_MS, BASE_MS * 2 ** attempt);

  // 절반은 고정, 절반은 랜덤 → 재연결 시점을 흩뿌린다
  return base / 2 + Math.random() * (base / 2);
}
```

**`retryAfterMs`를 받았을 때도 랜덤 지연은 그대로 적용합니다.** 서버가 모든 클라이언트에게 같은 값을 보내기 때문에, 그대로 쓰면 다시 한 지점에 몰립니다.

### 5-3. 재연결 루프

```ts
async function connectWithRetry() {
  let attempt = 0;

  while (!stopped) {
    try {
      await sleep(backoffMs(attempt, pendingRetryAfterMs));
      pendingRetryAfterMs = null;

      const { ticket } = await issueTicket();   // 대기 후에 발급 (3-3 규칙)
      await openSocket(ticket);

      attempt = 0;                              // 성공 시 초기화
      await resubscribeAll();
      await refetchAfterReconnect();            // 7장 — 필수
      return;
    } catch (e) {
      if (isUnauthorized(e)) return;            // 로그인 만료 → 루프 중단
      attempt += 1;
    }
  }
}
```

**성공 시 `attempt`를 반드시 0으로 되돌려야 합니다.** 안 그러면 다음 끊김에서 곧바로 30초를 기다리게 됩니다.

### 5-4. 앱이 백그라운드로 갈 때

모바일에서는 백그라운드 진입 시 소켓 유지가 보장되지 않습니다.

- **백그라운드 진입**: 연결을 명시적으로 정리하고 재연결 루프를 멈춥니다
- **포그라운드 복귀**: 연결을 새로 맺고, **7장의 재조회를 반드시 수행**합니다

백그라운드에 있던 시간만큼 데이터 공백이 생기므로, 복귀 시 재조회는 선택이 아닙니다.

## 6. `connection.draining` 처리

### 6-1. 무엇인가

서버가 종료되기 직전에 **"이 연결은 곧 끊긴다"고 미리 알려주는 신호**입니다. 배포 중 롤링 재시작 시 발송됩니다.

이게 없으면 클라이언트는 연결이 실제로 끊어질 때까지 아무것도 모릅니다. 그 사이 사용자가 보낸 메시지는 전송에 실패합니다.

### 6-2. 수신 형태

**구독 주소**: `/user/queue/connection/control`

```json
{
  "v": 1,
  "kind": "control",
  "type": "connection.draining",
  "payload": {
    "reason": "deploy",
    "retryAfterMs": 3000
  }
}
```

| `reason` | 의미 |
|---|---|
| `deploy` | 배포로 인한 재시작 |
| `maintenance` | 점검 |
| `overload` | 과부하로 인한 연결 정리 |
| `realtime_disabled` | 실시간 기능 일시 중단 |

> `retryAfterMs`는 **`null`일 수 있습니다.** 이 경우 5장의 기본 백오프를 사용하세요.

### 6-3. 처리 방법

```ts
function onDraining(payload: { reason: string; retryAfterMs: number | null }) {
  pendingRetryAfterMs = payload.retryAfterMs;

  // 1. 새 전송을 막고, 보내는 중이던 것은 재연결 후 재시도 큐로
  suspendOutbound();

  // 2. 서버가 끊기를 기다리지 말고 먼저 정리한다
  closeSocket();

  // 3. 재연결 루프 시작 (retryAfterMs 반영됨)
  connectWithRetry();
}
```

**UI 처리 기준**

- `reason`이 `deploy` / `maintenance`: **사용자에게 노출하지 않습니다.** 수 초 내 자동 복구되므로 배너를 띄우면 오히려 불안을 줍니다
- `realtime_disabled`: 복구가 오래 걸릴 수 있으므로 "실시간 갱신이 일시 중단되었습니다" 수준의 안내를 고려합니다

> **서버 현황**: 이 신호를 **발송하는 코드는 아직 구현 전**입니다. 수신 계약(주소·스키마)은 확정되었으니 프론트에서 먼저 구현하셔도 됩니다. 서버 작업이 붙으면 그때부터 실제로 도착합니다.

## 7. 재연결 후 데이터 복구 (필수)

### 7-1. 왜 필요한가

**연결이 끊겨 있던 동안 발생한 이벤트는 클라이언트에 영원히 도착하지 않습니다.**

서버는 실시간 이벤트를 보관했다가 나중에 다시 보내주지 않습니다. 보낼 시점에 받을 연결이 없으면 그대로 버립니다.

중요한 건 **데이터가 사라진 게 아니라는 점**입니다. 메시지는 DB에 정상적으로 저장되어 있습니다. 유실되는 건 "알림"뿐입니다. 그래서 **REST API로 다시 불러오면 완전히 복구됩니다.**

### 7-2. 무엇을 해야 하는가

**재연결에 성공하면, 조건 없이 아래를 재조회합니다.**

```ts
async function refetchAfterReconnect() {
  await fetchChatRooms();                 // 방 목록 (안 읽음 수 포함)

  if (currentRoomId) {
    await fetchMessages(currentRoomId);   // 열려 있는 방의 최신 메시지
  }
}
```

"끊긴 시간이 짧으니 건너뛰자" 같은 최적화는 하지 마세요. 1초만 끊겨도 그 사이 메시지는 유실됩니다.

### 7-3. 핵심 원칙

> **실시간 이벤트는 "빠른 알림"일 뿐이고, 데이터의 진짜 출처는 항상 REST API입니다.**

이 원칙은 `chat.changed` 이벤트의 설계에도 이미 반영되어 있습니다. 이 이벤트는 변경된 내용을 담고 있지 않고 **`roomId`만** 담고 있습니다. "이 방이 바뀌었으니 다시 조회하라"는 신호이지, 데이터 전달 수단이 아닙니다.

읽음 표시도 같은 원칙을 따릅니다. `chat.read.advanced`를 놓쳐도 `GET /api/v1/chat/rooms/{roomId}/messages`의 `lastReadMessageId`로 복구됩니다.

## 7-A. 읽음 표시 (`chat.read.advanced`)

### 7-A-1. 언제 오는가

**상대가 메시지를 읽어 읽음 위치가 앞으로 이동했을 때**, 그 방을 구독 중인 나에게 옵니다. 내가 읽음 처리했을 때 나에게는 오지 않습니다 (내 결과는 `/user/queue/chat/commands`의 `chat.read.committed`로 옵니다).

```json
{
  "v": 1,
  "kind": "event",
  "type": "chat.read.advanced",
  "eventId": "...",
  "occurredAt": "...",
  "payload": {
    "roomId": "1024",
    "lastReadMessageId": "88123"
  }
}
```

`lastReadMessageId`는 **상대가 읽은 마지막 메시지 id**입니다. 이 id 이하의 내 메시지에 읽음 표시를 그리시면 됩니다.

### 7-A-2. 받은 값을 그대로 반영하시면 됩니다

**서버가 순서와 단조 증가를 보장합니다.** 받은 `lastReadMessageId`를 그대로 저장하세요.

```ts
setPartnerLastRead(payload.lastReadMessageId);
```

크기 비교로 걸러내실 필요가 없습니다. 오히려 **직접 비교하지 마세요.** id는 문자열이라 `"1000" > "999"`가 `false`가 되어, 999→1000처럼 자릿수가 바뀌는 순간 새 값을 버리게 됩니다. 꼭 비교해야 한다면 `BigInt(a) > BigInt(b)`를 쓰세요.

서버가 보장하는 것은 두 가지입니다.

- **프레임이 발행 순서대로 도착합니다.** 100 다음에 105를 발행했다면 그 순서로 갑니다.
- **뒤로 가는 값은 발행되지 않습니다.** 읽음 위치가 실제로 전진했을 때만 프레임이 나가므로, 재시도로 같은 커서를 여러 번 보내도 중복 프레임이 오지 않습니다.

### 7-A-3. 초기값과 복구

방에 들어갈 때와 재연결 직후에는 `GET /api/v1/chat/rooms/{roomId}/messages` 응답의 **`lastReadMessageId`** 로 초기화합니다. 같은 의미의 값이고, 상대가 아직 아무것도 읽지 않았으면 `null`입니다.

## 8. 중복 메시지 제거

### 8-1. 왜 생기는가

7장의 재조회를 하면 **필연적으로 중복이 발생합니다.** 이미 실시간으로 받아 화면에 그린 메시지를, 재조회 결과로 한 번 더 받기 때문입니다.

### 8-2. 기준 키: `messageId`

```ts
const seen = new Set<string>();   // messageId는 문자열 (4-3 참고)

function appendMessage(m: ChatMessage) {
  if (seen.has(m.messageId)) return;

  seen.add(m.messageId);
  render(m);
}
```

### 8-3. `clientMsgId`를 중복 제거에 쓰면 안 됩니다

```json
{
  "messageId": "88123",
  "senderType": "them",
  "clientMsgId": null
}
```

`clientMsgId`는 **`senderType`이 `me`일 때만 값이 채워집니다.** 상대방이 보낸 메시지에는 항상 `null`이라 중복 제거 기준이 될 수 없습니다.

이 필드의 용도는 따로 있습니다. **"내가 방금 보내서 화면에 미리 띄워둔 임시 메시지"와 "서버가 확정한 실제 메시지"를 짝지어 교체**하는 것입니다. 두 용도를 섞지 마세요.

### 8-4. 정렬

메시지 정렬은 `messageId`가 아니라 **`sentAt` 기준**으로 하시고, 동일 시각이면 `messageId`로 보조 정렬하시면 됩니다.

## 9. heartbeat 설정

### 9-1. 왜 필요한가

서버를 여러 대로 늘리면 앞단에 **로드밸런서**가 놓입니다. 로드밸런서는 **일정 시간 아무 데이터도 오가지 않는 연결을 자동으로 끊습니다**(기본 60초).

채팅은 몇 분씩 조용할 수 있으므로, 그대로 두면 대화가 없을 때마다 연결이 끊깁니다.

### 9-2. 설정 값

서버는 **25초 양방향**으로 설정되어 있습니다. 클라이언트도 STOMP `CONNECT` 프레임에서 이 값을 수용해야 합니다.

```ts
const client = new Client({
  brokerURL: `wss://${host}/ws/v1/?ticket=${ticket}`,
  heartbeatIncoming: 25_000,
  heartbeatOutgoing: 25_000,
});
```

> ⚠️ 이 값이 `0`이면 **"신호를 주고받지 않겠다"** 는 선언이 되어 서버 설정이 무력화됩니다. 라이브러리 기본값이 `0`인 경우가 있으니 반드시 확인해 주세요.

## 11. 서버 측 진행 상황

프론트 작업 순서를 정하시는 데 참고하시라고 함께 적습니다.

| 항목 | 상태 |
|---|---|
| 티켓 발급 / 핸드셰이크 인증 | ✅ 구현 완료. 서버 확장 후에도 동작 동일 |
| `connection.draining` 수신 계약 (주소·스키마) | ✅ 확정 |
| `connection.draining` **발송** | ⏳ 미구현. 서버 종료 절차와 함께 작업 예정 |
| 서버 간 메시지 전달 (다중 인스턴스 대응) | ⏳ 미구현 |

**5·7·8·9장(재연결, 갭 복구, 중복 제거, heartbeat)은 서버 작업을 기다릴 필요가 없습니다.** 지금 서버가 1대인 상태에서도 네트워크 끊김과 배포는 발생하므로, 넣는 즉시 효과가 있습니다.

오히려 **이 작업들이 서버 확장보다 먼저** 되어야 합니다. 클라이언트가 끊김에 대비되지 않은 채로 서버 대수만 늘리면, 끊김 빈도는 늘어나는데 복구 능력은 그대로여서 장애 지점만 많아집니다.
