# AI 서버 인프라 변경 가이드 (RDS 분리 · 호출 출처 제한)

이 문서는 [ai-server-deploy-guide.md](ai-server-deploy-guide.md) 이후 확정된 인프라 변경을 담습니다.
**기존 가이드의 2-6절(데이터베이스)과 충돌하는 내용은 이 문서가 우선합니다.** 나머지 절(VPC, 서브넷,
보안그룹, ECR, 배포 파이프라인 등)은 기존 가이드 그대로 유효합니다.

---

## 1. 이전 가이드에서 바뀐 것

| 항목 | 이전 (기존 가이드 2-6절) | 현재 |
| --- | --- | --- |
| 데이터베이스 | 백엔드 RDS(MySQL) 인스턴스를 공유. `twinly_ai` 계정·데이터베이스로 격리 | **AI 전용 RDS 를 stage / prod 각각 신설.** 인스턴스 차원에서 완전 분리 |
| DB 엔진 | MySQL 8.4 고정 (백엔드와 같은 인스턴스이므로) | **AI 팀이 자유롭게 선택** (PostgreSQL 등) |
| `twinly_ai` 계정 / 데이터베이스 | 백엔드 RDS 에 생성 완료, 비밀번호 설정 후 사용 예정 | **폐기 예정. 쓰지 마세요** |
| 백엔드 RDS 사양 | `db.m7g.large` (prod 는 Multi-AZ) | `db.t4g.micro` / Single-AZ 로 축소 (배포 전이므로) — AI 팀에 직접 영향은 없으나 아래 권장 사양의 근거가 됩니다 |
| 백엔드 호출 경로 | 퍼블릭 도메인 호출 (기존 가이드 3절) | 경로는 동일. **`/internal/*` 에 호출 출처 제한 적용됨** (2절 참고) |

분리로 바꾼 이유는 세 가지입니다.

- **장애 격리** — AI 쪽 무거운 쿼리나 커넥션 문제가 백엔드 운영 DB 에 닿을 수 없습니다.
- **엔진 자유** — MySQL 에 맞출 필요가 없어져 pgvector 같은 엔진 전용 기능을 쓸 수 있습니다.
- **운영 독립** — 백업·복구·파라미터·버전 업그레이드를 서로 눈치 보지 않고 결정합니다.

공유로 아끼려던 비용은 `db.t4g.micro` 기준 대당 월 약 $18 이라, 위 이점과 맞바꿀 수준이 아니라고
판단했습니다.

---

## 2. 백엔드 호출 — 출처 제한 (기존 가이드 3절 보강)

호출 경로 자체는 기존 가이드 3절 그대로입니다.

```
AI 서버 → NAT → 인터넷 → ALB → API 인스턴스
```

여기에 한 가지가 추가됐습니다. **`/internal/*` 경로는 AI 서버에서 온 호출만 통과하도록
ALB 에서 제한되어 있습니다** (백엔드가 적용 완료, AI 팀이 준비할 것은 없습니다). AI 서버의
아웃바운드는 NAT EIP(기존 가이드 1-3 참고)로 나가므로 그 IP 만 허용되고, 그 외 출처는
ALB 가 403 으로 차단합니다.

따라서 **로컬 PC 나 다른 서버에서 internal API 를 직접 호출하면 차단됩니다.**
연동 테스트는 stage 의 AI 서버 인스턴스 위에서 하세요. 호출은 지금처럼 주입된
베이스 URL 을 그대로 쓰면 됩니다.

| 환경 | 베이스 URL |
| --- | --- |
| stage | `https://stage-api.trytwinly.com` |
| prod | `https://api.trytwinly.com` |

## 3. 데이터베이스 — AI 전용 RDS 분리 (기존 가이드 2-6절 대체)

AI 서버는 **자체 RDS 인스턴스를 stage / prod 각각 띄웁니다.** 백엔드 RDS(MySQL)와는
인스턴스 차원에서 완전히 분리되므로, 엔진·버전·마이그레이션·백업 모두 AI 팀이
결정하고 운영합니다.

> 백엔드 RDS 에 만들어져 있던 `twinly_ai` 계정과 `twinly_ai` 데이터베이스는 공유안의
> 잔재이며 폐기 예정입니다. 접속 정보를 받았더라도 **쓰지 마세요.**

### 3-1. 권장 사양

| 항목 | 권장값 | 이유 |
| --- | --- | --- |
| 클래스 | `db.t4g.micro` | 배포 전이므로 최소로 시작. 클래스 상향은 수 분짜리 온라인 작업이라 미리 키울 이유가 없습니다 |
| 배포 옵션 | Single-AZ | 서비스 오픈 후 필요해지면 Multi-AZ 는 온라인으로 켤 수 있습니다 |
| 스토리지 | gp3 20GiB | 자동 확장 상한만 넉넉히 잡으세요 |
| 비용 | 대당 월 약 $18 | 서울 리전 온디맨드 기준 (MySQL·PostgreSQL 동일 단가) |

`t4g.micro` 특성 두 가지는 알아두세요.

- **버스터블**입니다. 기준 성능은 vCPU 당 10% 이고 그 이상은 CPU 크레딧으로 냅니다.
  RDS 의 T 계열은 unlimited 모드라 크레딧이 바닥나면 느려지는 대신 초과 비용이 청구됩니다.
- 메모리가 1GiB 라 **max_connections 가 낮습니다** (백엔드 MySQL micro 실측 60).
  애플리케이션 커넥션 풀을 작게(5 안팎) 잡고, 서버 수 × 풀 크기가 한도를 넘지 않게 하세요.
  Performance Insights 도 micro 는 지원하지 않습니다.

### 3-2. 이름 규칙

리소스 이름은 `twinly-{env}-{service}-{자원}` 형식입니다. `{env}` 는 환경 이름으로
`stage` 또는 `prod`, `{service}` 는 백엔드가 `api`, AI 가 `ai` 입니다.
백엔드 쪽 실제 이름을 참고삼아 나란히 적으면 이렇습니다.

| 자원 | 백엔드 (참고) | AI (이렇게 만드세요) |
| --- | --- | --- |
| RDS 인스턴스 | `twinly-{env}-api-rds` | `twinly-{env}-ai-rds` |
| RDS 보안그룹 | `twinly-{env}-api-rds-sg` | `twinly-{env}-ai-rds-sg` |
| CloudWatch 알람 | `twinly-{env}-api-rds-{지표}` | `twinly-{env}-ai-rds-{지표}` (예: `twinly-prod-ai-rds-free-storage`) |
| RDS 이벤트 구독 | `twinly-{env}-api-rds-events` | `twinly-{env}-ai-rds-events` |

이벤트 구독만 **prod 에만** 둡니다. 이벤트 구독은 failover·가용성 상실 같은 인스턴스 수준
사건을 SNS 로 즉시 통지하는 장치라, 사람이 바로 대응해야 하는 prod 에서만 의미가 있습니다.
stage 장애는 개발 중에 바로 드러나므로 통지를 두면 알림 노이즈만 늘어납니다(백엔드도 같은
이유로 prod 만 둡니다).

엔드포인트 DNS(`twinly-{env}-ai-rds.<계정 해시>.ap-northeast-2.rds.amazonaws.com`)는
인스턴스 식별자를 따라 자동 생성되므로 따로 지을 것이 없습니다. 대신 **식별자를 나중에
바꾸면 엔드포인트도 같이 바뀌어 접속 설정을 전부 손봐야 하니, 처음부터 규칙대로 지으세요.**

두 서비스가 공유하는 자원은 서비스 접두어 없이 씁니다. DB 서브넷 그룹
`twinly-{env}-db-subnet-group` 이 그 예이고, 그래서 이름을 그대로 재사용합니다(3-3).

### 3-3. 네트워크

새로 만들 서브넷은 없습니다. **기존 DB 서브넷 그룹을 그대로 재사용**하세요.

| 항목 | stage | prod |
| --- | --- | --- |
| DB 서브넷 그룹 | `twinly-stage-db-subnet-group` | `twinly-prod-db-subnet-group` |
| 구성 서브넷 | `private-db-a/c` (`10.0.48.0/24`, `10.0.49.0/24`) | 동일 계층 (`10.1.48.0/24`, `10.1.49.0/24`) |

보안그룹만 새로 만듭니다. `twinly-{env}-ai-rds-sg` 를 만들고, 인바운드는
**DB 포트(PostgreSQL 이면 5432)를 `twinly-{env}-ai-sg`(AI 서버 SG) 출처로만** 여세요.
CIDR 로 열지 말고 반드시 SG 출처로 지정해야 인스턴스를 교체해도 규칙을 고칠 일이 없습니다.
백엔드 RDS 의 SG 에는 아무것도 추가하지 않습니다.

AI 서버를 `private-ai` 서브넷에 올려야 한다는 원칙(기존 가이드 1-2)은 그대로입니다.
이제 근거는 DB 계정의 IP 대역 제한이 아니라, 보안그룹과 ALB 출처 제한이 이 서브넷
경계를 기준으로 동작한다는 점입니다.

### 3-4. 접속 정보 관리

- 호스트·계정·비밀번호는 AI 팀이 인스턴스를 만들면서 직접 정하고,
  `/twinly/{env}/ai/env` SSM 파라미터에 기록해서 쓰세요 (기존 가이드 2-4 방식 그대로).
- 마스터 계정을 애플리케이션에 넣지 말고, 애플리케이션 전용 계정을 따로 만들어 쓰는 것을
  권장합니다.

### 3-5. 분리이기 때문에 달라지는 것

- 백업·특정 시점 복구가 AI 데이터만 독립적으로 됩니다. 백엔드와 서로 영향이 없습니다.
- 스토리지·커넥션·파라미터 그룹을 나눠 쓰지 않으므로 상호 간섭이 없습니다.
- 대신 인스턴스 운영(알람, 용량, 버전 업그레이드)도 AI 팀 몫입니다. 최소한
  FreeStorageSpace(스토리지 고갈)와 CPUSurplusCreditsCharged(크레딧 초과 과금) 알람은
  걸어두세요.
