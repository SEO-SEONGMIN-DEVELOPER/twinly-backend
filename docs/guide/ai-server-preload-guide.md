# AI 서버 선생성(preload) 요청 수신 가이드

백엔드가 **가입 직후 유저에 대해 AI 서버를 호출**하고, AI 서버가 그 유저의 2일치 시뮬레이션을
앞당겨 만들어 제출하는 흐름입니다. AI 서버에 **인바운드가 처음 생기는 변경**이라, AI 팀이
준비해야 할 것을 여기에 모았습니다.

기존 배치 흐름([internal-api-for-ai_v1.md](../api-spec/internal-api-for-ai_v1.md))은 그대로
유지됩니다. 이 문서는 거기에 얹히는 추가 경로만 다룹니다.

> **아직 확정 전인 값이 있습니다.** 서비스 포트, 엔드포인트 경로는 AI 팀과 합의해서 정합니다.
> 이 문서의 값은 제안이며, 합의되면 그 값으로 갱신합니다.

---

## 1. 왜 필요한가

지금은 **다음 날의 시뮬레이션을 그 전날 하루에 걸쳐 생성**하는 구조입니다. 그래서 오늘 가입한
유저는 이렇게 됩니다.

| 일자 | 상태 |
| --- | --- |
| D+0 (가입일) | 볼 콘텐츠 없음 |
| D+1 | 볼 콘텐츠 없음 (전날 배치에 이 유저가 없었으므로) |
| D+2 | 첫 시뮬레이션 노출 |

**신규 가입자와 재가입자가 이틀을 빈 화면으로 보냅니다.** 온보딩 직후 이탈이 가장 많은
구간이라 그대로 둘 수 없습니다.

그래서 백엔드가 가입 완료 시점에 AI 서버로 "이 유저의 D+0, D+1 회차를 지금 만들어 달라"고
요청합니다. AI 서버는 접수만 하고 즉시 응답하며, 결과는 **기존 제출 API 를 그대로 써서**
비동기로 돌려줍니다.

## 2. 전체 그림

```
[신규]  백엔드 API 인스턴스 → internal ALB → AI 인스턴스
        POST /internal/v1/simulations/preload      (접수만, 즉시 202)

[기존]  AI 인스턴스 → NAT → 인터넷 → 퍼블릭 ALB → 백엔드 API 인스턴스
        GET  /internal/v1/users/{userId}/persona   (입력 확보)
        POST /internal/v1/users/{userId}/simulations  (결과 제출)
```

**두 흐름은 서로 다른 요청입니다.** 요청과 결과가 같은 커넥션으로 오가지 않습니다. 백엔드는
202 를 받는 순간 그 커넥션을 놓고, 결과는 나중에 AI 서버가 새 요청으로 밀어 넣습니다.

동기로 만들지 않은 이유는 하나입니다. **LLM 생성은 분 단위이고, 그동안 백엔드 스레드와
커넥션이 잡혀 있으면 가입 API 전체가 AI 서버의 응답 속도에 묶입니다.** 접수와 제출을 끊어두면
AI 쪽이 아무리 오래 걸려도 백엔드는 영향을 받지 않습니다.

## 3. 역할 분담

| # | 항목 | 담당 |
| --- | --- | --- |
| 1 | internal ALB 생성 (`twinly-{env}-internal-alb`) | 백엔드 |
| 2 | ALB 보안그룹 생성 (`twinly-{env}-internal-alb-sg`) | 백엔드 |
| 3 | 타깃 그룹 생성 (`twinly-{env}-ai-tg`) | 백엔드 |
| 4 | 백엔드에서 AI 서버를 호출하는 클라이언트 구현 | 백엔드 |
| 5 | **`twinly-{env}-ai-sg` 인바운드 규칙 추가** | **AI 팀** |
| 6 | **인바운드 웹서버 기동 + 헬스체크 엔드포인트** | **AI 팀** |
| 7 | **선생성 엔드포인트 구현 (5절)** | **AI 팀** |
| 8 | **타깃 그룹에 인스턴스 등록** | **AI 팀** |

4절부터가 AI 팀 몫입니다.

## 4. 네트워크 준비

### 4-1. 보안그룹 인바운드 추가

지금 `twinly-{env}-ai-sg` 의 인바운드는 모니터링 SG 의 메트릭 포트 하나뿐입니다
([ai-server-deploy-guide.md](ai-server-deploy-guide.md) 2-1). 여기에 한 줄을 더합니다.

| 방향 | 포트 | 출처 | 이유 |
| --- | --- | --- | --- |
| 인바운드 | 메트릭 포트 | `twinly-{env}-monitoring-sg` | 기존 |
| 인바운드 | **서비스 포트(8000 제안)** | **`twinly-{env}-internal-alb-sg`** | **신규.** ALB 가 전달하는 요청 |

**CIDR 이 아니라 SG 를 출처로 지정하세요.** ALB 노드의 사설 IP 는 확장·교체 때 바뀌지만 SG 는
그대로이므로, SG 출처로 걸면 규칙을 다시 손댈 일이 없습니다.

`twinly-{env}-internal-alb-sg` 는 백엔드가 먼저 만들어 SG ID 를 전달합니다. **그 전에는 이
규칙을 만들 수 없으니 순서를 지켜주세요.**

### 4-2. 타깃 그룹 등록

백엔드가 만든 `twinly-{env}-ai-tg` 에 AI 인스턴스 2 대(a/c)를 등록합니다.

**인스턴스를 교체하면 등록도 다시 해야 합니다.** Prometheus 대상 IP 를 고쳐야 하는 것과 같은
성격의 수동 작업입니다([ai-server-deploy-guide.md](ai-server-deploy-guide.md) 2-1 참고).
인스턴스 교체 절차서에 두 항목을 나란히 적어두시길 권합니다.

### 4-3. 프로토콜과 인증

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 프로토콜 | **HTTP 평문** | VPC 안에서만 오가는 사설 경로입니다. 내부 도메인용 인증서를 발급·갱신하는 비용을 지금 질 이유가 없습니다 |
| 애플리케이션 인증 | **없음** | 백엔드의 `/internal/*` 과 같은 원칙입니다. 보호는 보안그룹 경계가 전담합니다 |

즉 **서비스 포트에 도달한 요청은 백엔드가 보낸 것으로 신뢰합니다.** 그 신뢰가 성립하려면
4-1 의 인바운드가 반드시 `internal-alb-sg` 출처로만 열려 있어야 합니다. `0.0.0.0/0` 이나
VPC CIDR 로 열면 이 전제가 무너집니다.

## 5. 구현해야 할 엔드포인트

### 5-1. 헬스체크

| 항목 | 값 |
| --- | --- |
| 경로 | `GET /health` |
| 응답 | `200`, 본문 무관 |

ALB 가 이걸로 살아 있는 인스턴스를 고릅니다. **여기에 DB 나 LLM 연결 검사를 넣지 마세요.**
의존성이 잠깐 흔들릴 때 두 대가 동시에 타깃에서 빠지면, 정작 요청을 받을 곳이 없어져 복구가
더 어려워집니다. **프로세스가 살아 있는지만** 보면 됩니다.

### 5-2. 선생성 요청 수신

| 항목 | 값 |
| --- | --- |
| 경로 | `POST /internal/v1/simulations/preload` |
| 성공 응답 | **`202 Accepted`, 본문 없음** |

#### Request Body

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `userId` | string(숫자) | O | 대상 유저 ID. 숫자 ID 를 문자열로 주고받는 규칙은 기존과 동일합니다 |
| `dates` | string(`YYYY-MM-DD`)[] | O | 만들어야 할 회차 목록. **KST 기준 달력 날짜**이며 보통 2개(D+0, D+1)입니다 |

```json
{
  "userId": "12",
  "dates": ["2026-09-02", "2026-09-03"]
}
```

**`dates` 의 값을 그대로 `POST /internal/v1/users/{userId}/simulations` 의 `date` 로 되돌려
보내주세요.** 백엔드는 이 키로 회차를 식별합니다. 여기서 값이 어긋나면 유저는 여전히 빈
화면을 봅니다.

개수는 고정으로 가정하지 마세요. 지금은 2개지만 정책이 바뀌면 1개나 3개가 올 수 있습니다.
**받은 배열을 그대로 순회**하도록 구현해주세요.

#### 응답 규약

| HTTP | 언제 |
| --- | --- |
| `202` | 접수 완료. **생성 완료가 아니라 "받았다"는 뜻입니다** |
| `400` | `userId` 가 숫자가 아님 / `dates` 가 비었거나 형식 오류 |
| `5xx` | AI 서버 내부 오류. 백엔드가 재시도 대상으로 분류합니다 |

**생성 결과를 응답에 담지 마세요.** 백엔드는 202 만 확인하고 곧바로 커넥션을 놓습니다.

백엔드 쪽 타임아웃은 **connect 2 초 / read 3 초**로 잡습니다. 접수 응답이 이 안에 떨어져야
하므로, **요청 스레드에서 LLM 을 호출하면 안 됩니다.** 큐에 넣고 즉시 202 를 반환하세요.

## 6. 반드시 지켜야 할 것

### 6-1. 작업 상태는 인스턴스 로컬이 아니라 RDS 에

ALB 가 a/c 두 대 중 어디로 꽂을지는 요청마다 다릅니다. **접수한 인스턴스와 처리하는 인스턴스가
다를 수 있고, 처리 중 인스턴스가 교체될 수도 있습니다.**

메모리 큐나 로컬 파일에 작업을 쌓으면 그 인스턴스가 죽는 순간 요청이 조용히 사라집니다.
백엔드는 이미 202 를 받았으므로 **아무도 유실을 모릅니다.** 접수 즉시 AI 전용 RDS 에
작업 행을 남기고, 워커가 그걸 집어가는 형태로 만들어주세요.

### 6-2. 야간 배치와 같은 회차를 두 번 만들지 마세요

이게 가장 조심할 부분입니다. 백엔드의 `POST .../simulations` 는 같은 `(userId, date)` 로 다시
호출하면 **그 날짜의 데이터를 전부 지우고 새로 저장합니다.** 그리고 **유저가 이미 답변한
질문의 응답도 함께 지워집니다**([internal-api-for-ai_v1.md](../api-spec/internal-api-for-ai_v1.md) 4-1).

preload 로 만든 D+1 회차를 그날 밤 정기 배치가 다시 만들어 보내면, 유저가 낮에 답한 내용이
사라집니다. **preload 로 이미 제출한 `(userId, date)` 는 배치에서 건너뛰도록** AI 쪽에
기록을 남겨주세요. 백엔드에는 이걸 막아줄 장치가 없습니다.

### 6-3. 중복 요청은 무시하세요

백엔드는 타임아웃이나 5xx 에 재시도합니다. 같은 `(userId, date)` 요청이 두 번 올 수 있고,
**이미 접수했거나 처리 중이면 새 작업을 만들지 말고 202 만 돌려주세요.** 안 그러면 재시도
한 번이 LLM 호출 비용 두 배가 됩니다.

### 6-4. 실패 후 재시도는 AI 팀 책임입니다

백엔드는 202 를 받은 시점에 손을 뗍니다. 그 뒤 생성이 실패해도 **백엔드는 알 방법이 없고,
다시 요청하지도 않습니다.** 유저는 이틀을 그대로 빈 화면으로 보내게 됩니다.

- 워커 단계에서 실패하면 AI 쪽에서 재시도해주세요
- 최종 실패는 **알람으로 띄워주세요.** 로그만 남기면 아무도 모릅니다
  ([ai-server-deploy-guide.md](ai-server-deploy-guide.md) 7-2 의 배치 알람과 같은 방식)

### 6-5. persona 403 / 404 는 그대로 적용됩니다

preload 도 결국 `GET .../persona` 로 입력을 받습니다. 백엔드는 권한이 있는 유저만 보내지만
결제 반영에 몇 분 지연이 있어, **접수 직후 조회하면 403 이 나올 수 있습니다.**

| 코드 | 뜻 | 할 일 |
| --- | --- | --- |
| 403 | 아직 구독 반영 전이거나 구독 없음 | **잠시 뒤 재시도.** 그래도 403 이면 생성 생략 |
| 404 | 파기 확정 | 생성 생략, 작업 폐기 |

여기서만 403 이 재시도 대상입니다. 정기 배치에서는 건너뛰는 게 맞습니다
([simulation-access-gate_v1.md](../api-spec/simulation-access-gate_v1.md)).

### 6-6. 배포 중 요청이 끊기지 않게

지금까지 AI 서버는 배치 전용이라 컨테이너를 아무 때나 내려도 됐습니다. **이제는 인바운드가
있으므로 배포 중에 요청이 유실될 수 있습니다.**

두 대를 동시에 내리지 말고, 타깃 그룹에서 한 대를 뺀 뒤 교체하고 다시 넣는 순서로 배포하세요.
지금 규모에서는 **배포 시간대에 도착한 요청 하나를 잃는 것**이 실제 위험입니다.

## 8. 자주 나오는 질문

**Q. 백엔드가 응답을 기다려주면 안 되나요? 그러면 상태 관리가 필요 없는데요.**
안 됩니다. 가입 API 가 LLM 생성 시간만큼 늘어나고, 그동안 백엔드 스레드와 DB 커넥션이 잡힙니다.
가입이 몰리면 그대로 장애가 됩니다. 유저 입장에서도 "가입 버튼이 3 분 도는 것"보다
"들어가 보니 콘텐츠가 있는 것"이 낫습니다.

**Q. 웹서버와 배치를 한 컨테이너에 같이 둬도 되나요?**
됩니다. 다만 배치가 도는 동안 웹서버 응답이 느려지지 않게만 해주세요. 파이썬이면 배치를
별도 프로세스나 워커로 분리하는 편이 안전합니다.

**Q. D+0 요청이 왔는데 그날이 이미 절반쯤 지났으면요?**
남은 시간대만 만드시면 됩니다. 회차 안의 시각은 AI 가 정하는 값이고 백엔드는 검증하지
않습니다. 다만 **이미 지나간 시각의 장면을 넣으면 유저에게 과거로 보입니다.**

**Q. 요청이 온 유저가 이미 우리 DB 에 있으면요?**
재가입자입니다. 기존 이력을 이어 쓰시면 됩니다. 백엔드의 `userId` 는 재가입해도 같은 값을
유지하지 않을 수 있으니, **요청에 담긴 `userId` 를 기준으로만** 판단하세요.

**Q. 백엔드가 요청을 보냈는지 어떻게 확인하나요?**
`/twinly/{env}/ai` CloudWatch 로그 그룹에 접수 로그를 남겨주세요. 백엔드도 호출 로그를 남기므로
양쪽 로그를 대조하면 유실 구간이 바로 드러납니다.

**Q. prod 에도 같은 구성인가요?**
같습니다. 이름만 `stage` → `prod` 로 바뀌고, 리소스는 환경별로 따로 만듭니다. stage 에서
종단 검증을 마친 뒤 prod 로 넘어갑니다.
