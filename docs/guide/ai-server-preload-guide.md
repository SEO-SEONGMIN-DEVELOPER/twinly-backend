# AI 서버 선생성(preload) 요청 수신 가이드

백엔드가 **유저에게 시뮬레이션 권한이 생긴 직후 AI 서버를 호출**하고, AI 서버가 그 유저의
2일치 시뮬레이션을 앞당겨 만들어 제출하는 흐름입니다. AI 서버에 인바운드가 처음 생기는
변경입니다.

기존 배치 흐름([internal-api-for-ai_v1.md](../api-spec/internal-api-for-ai_v1.md))은 그대로
유지됩니다. 네트워크와 로드밸런서는 백엔드가 만들어두었으므로, **AI 팀이 할 일은 정해진
포트로 웹서버를 띄우고 엔드포인트 두 개를 구현하는 것입니다.**

---

## 1. 왜 필요한가

지금은 다음 날의 시뮬레이션을 그 전날 배치로 만듭니다. 오늘 결제한 유저는 전날 배치에
없었으므로 D+0, D+1 이 비고 D+2 부터 보입니다. 이 이틀을 없애기 위해, 백엔드가 결제를
DB 에 반영한 시점에 "이 유저의 D+0, D+1 을 지금 만들어 달라"고 요청합니다.

### 언제 요청이 오는가

트리거는 가입이 아니라 **시뮬레이션 권한(`simulation_access`)이 없다가 생기는 순간**입니다.

| 상황 | 요청 |
| --- | --- |
| 가입만 하고 결제하지 않음 | 안 옴 |
| 첫 결제가 백엔드 DB 에 반영됨 | **옴** |
| 구독 갱신 (권한이 이어짐) | 안 옴 |
| 만료 후 재결제 (권한이 다시 생김) | **옴** |
| 탈퇴 후 재가입하고 결제 | **옴** (새 `userId` 로) |

---

## 2. 전체 그림

```
[신규]  백엔드 API 인스턴스 → internal ALB :8000 → AI 인스턴스 :8000
        POST /internal/v1/simulations/preload      (접수만, 즉시 202)

[기존]  AI 인스턴스 → internal ALB :8080 → 백엔드 API 인스턴스 :8080
        GET  /internal/v1/users/{userId}/persona   (입력 확보)
        POST /internal/v1/users/{userId}/simulations  (결과 제출)
```

기존 경로도 이제 인터넷을 거치지 않습니다. 베이스 URL 은 [internal-alb-guide.md](internal-alb-guide.md) 를 보세요.

요청과 결과는 서로 다른 커넥션입니다. 백엔드는 202 를 받는 순간 손을 떼고, 결과는 AI 서버가
기존 제출 API 로 밀어 넣습니다. LLM 생성은 분 단위라 동기로 기다리면 결제 웹훅 처리가
AI 서버 응답 속도에 묶이기 때문입니다.

## 3. 역할 분담

| 항목 | 담당 | stage | prod |
| --- | --- | --- | --- |
| internal ALB, ALB 보안그룹, 타깃 그룹 생성 | 백엔드 | 완료 | 완료 |
| `twinly-{env}-ai-sg` 인바운드 규칙 추가 | 백엔드 | 완료 | AI 인스턴스 생성 후 |
| 타깃 그룹에 AI 인스턴스 등록 | 백엔드 | 완료 (a/c 2 대) | AI 인스턴스 생성 후 |
| 결제 반영 시 AI 서버를 호출하는 클라이언트 | 백엔드 | 구현 완료 | 구현 완료 |
| **웹서버 기동 + 헬스체크 엔드포인트** | **AI 팀** | | |
| **선생성 엔드포인트 구현 (5절)** | **AI 팀** | | |

prod 는 `twinly-prod-ai-sg` 와 AI 인스턴스가 아직 없습니다. AI 팀이 만들면 SG ID 와 인스턴스 ID 를
백엔드에 전달해주세요. 남은 두 항목을 붙이겠습니다.

## 4. 네트워크

### 4-1. 확정값

| 항목 | 값 |
| --- | --- |
| 서비스 포트 | `8000` |
| 바인드 주소 | `0.0.0.0` (`127.0.0.1` 에 묶으면 ALB 가 닿지 못합니다) |
| 헬스체크 | `GET /health` → `200` |

타깃 그룹과 보안그룹에 이미 박혀 있는 값입니다. **바꾸려면 백엔드에 먼저 말씀해주세요.**

### 4-2. 신뢰 경계

`twinly-{env}-ai-sg` 인바운드는 `8000 ← twinly-{env}-internal-alb-sg` 로만 열려 있고, ALB 는
API 인스턴스에서 온 요청만 받습니다. **8000 포트에 도달한 요청은 백엔드가 보낸 것으로
신뢰**해도 됩니다. HTTP 평문이며 애플리케이션 인증은 없습니다.

### 4-3. 인스턴스를 교체할 때

타깃 그룹 등록은 인스턴스 ID 기준이라 **인스턴스를 새로 띄우면 등록이 사라집니다.** 교체 후
백엔드에 새 인스턴스 ID 를 전달해주세요. 지금 stage 에 등록된 인스턴스는
`twinly-stage-ai-a`(`i-0af06523d98ff485c`) 와 `twinly-stage-ai-c`(`i-083773ec7d5d11ac9`) 입니다.

## 5. 구현해야 할 엔드포인트

### 5-1. 헬스체크

| 항목 | 값 |
| --- | --- |
| 경로 | `GET /health` |
| 응답 | `200`, 본문 무관 |

**DB 나 LLM 연결 검사를 넣지 마세요.** 의존성이 잠깐 흔들릴 때 두 대가 동시에 타깃에서
빠집니다. 프로세스가 살아 있는지만 보면 됩니다.

### 5-2. 선생성 요청 수신

| 항목 | 값 |
| --- | --- |
| 경로 | `POST /internal/v1/simulations/preload` |
| 성공 응답 | **`202 Accepted`, 본문 없음** |

#### Request Body

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `userId` | string(숫자) | O | 대상 유저 ID |
| `grantedAt` | string(`YYYY-MM-DDTHH:mm:ss`) | O | **시뮬레이션을 시작할 시각.** 이 시각부터 결과를 만들어주세요. KST 기준, 오프셋 없는 로컬 시각, 초 단위입니다 |
| `dates` | string(`YYYY-MM-DD`)[] | O | 만들어야 할 회차 목록. `grantedAt` 의 날짜부터 시작하며 보통 2개(D+0, D+1)입니다 |

```json
{
  "userId": "12",
  "grantedAt": "2026-09-02T14:23:51",
  "dates": ["2026-09-02", "2026-09-03"]
}
```

- D+0 회차는 `grantedAt` 부터 그날 끝까지, D+1 회차는 하루 전체를 만듭니다. `grantedAt` 보다
  앞선 시각의 장면을 넣으면 유저에게 과거로 보입니다.
- **`dates` 의 값을 그대로 `POST .../simulations` 의 `date` 로 되돌려 보내주세요.** 백엔드는
  이 키로 회차를 식별합니다.
- 개수를 고정으로 가정하지 말고 **받은 배열을 그대로 순회**하세요.

#### 응답 규약

| HTTP | 언제 |
| --- | --- |
| `202` | 접수 완료. 생성 완료가 아니라 "받았다"는 뜻입니다 |
| `400` | `userId` 가 숫자가 아님 / `grantedAt` 형식 오류 / `dates` 가 비었거나 형식 오류 |
| `5xx` | AI 서버 내부 오류 |

생성 결과를 응답에 담지 마세요. 백엔드는 상태 코드만 봅니다.

#### 백엔드의 호출 규약

| 항목 | 값 |
| --- | --- |
| 타임아웃 | connect 2 초 / read 3 초 |
| 재시도 | 202 가 아니면(타임아웃, 4xx, 5xx 모두) 2 초 간격으로 최대 3 회 |
| 최종 실패 | 백엔드 에러 로그(`SIMULATION_PRELOAD_FAILED`). 이후 다시 요청하지 않음 |
| 성공 로그 | `시뮬레이션 선생성 요청 접수. userId=12, grantedAt=..., dates=[...]` |

접수 응답이 3 초 안에 떨어져야 하므로 **요청 스레드에서 LLM 을 호출하면 안 됩니다.** 작업을
기록하고 즉시 202 를 반환하세요. AI 쪽도 `/twinly/{env}/ai` 로그 그룹에 `userId` 와 `dates` 를
포함한 접수 로그를 남겨주세요. 양쪽 로그를 대조하면 유실 구간이 드러납니다.

## 6. 반드시 지켜야 할 것

### 6-1. 작업 상태는 인스턴스 로컬이 아니라 RDS 에

ALB 가 a/c 두 대 중 어디로 꽂을지는 요청마다 다릅니다. 접수한 인스턴스와 처리하는
인스턴스가 다를 수 있고, 처리 중 인스턴스가 교체될 수도 있습니다. 메모리 큐나 로컬 파일에
쌓으면 인스턴스가 죽는 순간 요청이 사라지고, 백엔드는 이미 202 를 받았으므로 아무도 모릅니다.
접수 즉시 AI 전용 RDS 에 작업 행을 남기고 워커가 집어가게 하세요.

### 6-2. 야간 배치와 같은 회차를 두 번 만들지 마세요

백엔드의 `POST .../simulations` 는 같은 `(userId, date)` 로 다시 호출하면 **그 날짜의 데이터를
전부 지우고 새로 저장하며, 유저가 이미 답변한 응답도 함께 지워집니다**
([internal-api-for-ai_v1.md](../api-spec/internal-api-for-ai_v1.md) 4-1). preload 로 만든 D+1 을
그날 밤 배치가 다시 보내면 유저가 낮에 답한 내용이 사라집니다. **preload 로 제출한
`(userId, date)` 는 배치에서 건너뛰도록** 기록을 남겨주세요. 백엔드에는 막아줄 장치가 없습니다.

### 6-3. 중복 요청은 무시하세요

백엔드는 실패로 판단하면 같은 요청을 최대 3 번 보내고, 결제 반영 경로가 두 개(웹훅, 앱
조회 시 지연 동기화)라 같은 유저의 요청이 거의 동시에 두 번 올 수도 있습니다. 같은
`(userId, date)` 를 **이미 접수했거나 처리 중이면 새 작업을 만들지 말고 202 만 돌려주세요.**

### 6-4. 실패 후 재시도는 AI 팀 책임입니다

백엔드는 202 를 받은 뒤 생성이 실패해도 알 방법이 없고 다시 요청하지도 않습니다. 워커
단계의 실패는 AI 쪽에서 재시도하고, 최종 실패는 알람으로 띄워주세요
([ai-server-deploy-guide.md](ai-server-deploy-guide.md) 7-2 의 배치 알람과 같은 방식).

### 6-5. persona 403 / 404

권한을 DB 에 반영한 뒤 요청하므로 보통은 200 이지만, 그 사이에 환불이나 탈퇴가 끼어들 수
있습니다.

| 코드 | 뜻 | 할 일 |
| --- | --- | --- |
| 403 | 권한이 사라짐 | 잠시 뒤 한 번 재시도. 그래도 403 이면 생성 생략 |
| 404 | 파기 확정 | 생성 생략, 작업 폐기 |

### 6-6. 배포는 한 대씩

인바운드가 생겼으므로 **두 대를 동시에 내리지 마세요.** 한 대를 교체하고 `/health` 가 200 을
돌려주는 것을 확인한 뒤 다음 대로 넘어가면 됩니다. 타깃 그룹은 백엔드가 관리하므로 직접
뺐다 넣을 필요는 없습니다.

타깃 그룹 헬스체크는 10 초 간격, 타임아웃 5 초, 2 회 연속 실패 시 제외, 2 회 연속 성공 시
복귀입니다. 컨테이너를 내린 뒤 **최대 20 초 동안은 그 인스턴스로 요청이 갈 수 있고**, 그
요청은 백엔드가 재시도해 다른 인스턴스로 보냅니다.

## 7. 체크리스트

- [ ] 웹서버를 `0.0.0.0:8000` 으로 기동
- [ ] `GET /health` 구현 (의존성 검사 없이 200)
- [ ] `POST /internal/v1/simulations/preload` 구현, 즉시 202 반환
- [ ] 접수 작업을 AI 전용 RDS 에 기록
- [ ] 워커가 회차별로 persona 조회 → 생성 → `POST .../simulations` 제출
- [ ] D+0 회차를 `grantedAt` 부터 시작하도록 구성
- [ ] preload 로 제출한 `(userId, date)` 를 정기 배치에서 제외
- [ ] 중복 요청 무시 처리
- [ ] 생성 최종 실패 알람
- [ ] 배포 시 한 대씩 순차 교체
- [ ] `/twinly/{env}/ai` 에 접수 로그
- [ ] stage 에서 종단 검증 (결제 → 접수 → 제출 → 앱에서 노출 확인)
