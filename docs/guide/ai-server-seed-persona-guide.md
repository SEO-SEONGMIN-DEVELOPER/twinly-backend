# 시드 페르소나 활용 가이드 (AI 서버용)

stage 에는 시뮬레이션 개발·테스트용 페르소나 **20명분**이 미리 채워져 있습니다. 실제 유저 가입을
기다리지 않고 바로 시뮬레이션을 돌려볼 수 있도록 백엔드가 부팅 시 자동으로 생성합니다.

**연동 방법은 기존과 같습니다.** 시드 유저 전용 API 는 없고, [internal-api-for-ai_v1.md](../api-spec/internal-api-for-ai_v1.md)
의 `GET /internal/v1/users` 와 `GET /internal/v1/users/{userId}/persona` 로 실제 유저와 똑같이 내려옵니다.
이 문서는 **그 20명이 어떤 데이터이고 무엇을 주의해야 하는지**만 다룹니다.

## 1. 무엇이 준비돼 있나

stage 에 `userId` **1~20** 으로 시드 유저 20명이 있습니다. 각자 페르소나 요소 42개를 가지고 있고,

| `communicationStyle` | 6 | `conflictStyle` | 3 |

| `openness` | 3 | `detail` | 5 |

## 2. 실제 유저와 같은 점, 다른 점

| 항목 | 시드 유저 | 실제 유저 |
| --- | --- | --- |
| API 경로·응답 스키마 | 동일 | 동일 |
| 이름·성별·학교·학과·생년월일 | 항상 채워짐 | 항상 채워짐 |
| 설문 8개 차원 | 항상 전부 채워짐 | 설문을 끝까지 마쳐야 채워짐 |
| `detail` 형식 | `"질문: 답변"` | `"질문: 답변"` |
| `detail` 개수 | 5개 고정 | 0~8개 (AI 인터뷰 진행 턴 수만큼) |
| `summary` | 항상 1개 | 항상 1개 |
| 설문 응답의 성격 | **난수로 A/B 결정** | 본인이 고른 값 |

가장 큰 차이는 마지막 줄입니다. 시드 유저의 설문 응답은 유저별 고정 시드 난수로 A/B 를 뽑은 것이라,
**사람이라면 잘 하지 않을 조합이 나올 수 있습니다.** 위 예시의 `extraversion` 만 봐도 "먼저 말을
꺼내 침묵을 깬다"와 "친한 소수와 조용히 이야기하는 자리에 간다"가 한 사람에게 같이 붙어 있습니다.

이건 버그가 아니라 시드 데이터의 성질입니다. 오히려 **프롬프트가 모순되는 성향을 받았을 때 어떻게
버티는지** 확인하기 좋은 재료이니, 그런 조합이 보이면 그대로 태워보시는 편이 낫습니다. 사람 같은
일관성이 전제여야 하는 검증이라면 실제 온보딩을 거친 계정을 따로 만드시는 게 맞습니다.

## 3. 주의사항

### 3-1. `userId` 1~28 이 다 내려오지만 21~28 은 쓸 게 없습니다

`GET /internal/v1/users` 는 stage 의 모든 유저를 내려줍니다. 현재 28명이고, 그중 **21~28 은 온보딩을
중간까지만 진행한 프론트·QA 테스트 계정**이라 페르소나가 거의 비어 있습니다.

| userId | `personaElements` 상태 |
| --- | --- |
| 1~20 | 11개 차원 전부, 42개 요소 |
| 21 | `interest` 5개뿐 |
| 22~28 | `interest` + `detail` 만, 5~7개 |

호출 자체는 200 으로 정상 응답하니 **에러로는 구분되지 않습니다.** 시뮬레이션 품질을 보실 때는
1~20 만 쓰시고, 21~28 은 "페르소나가 빈약할 때 프롬프트가 어떻게 되나" 를 보는 용도로만 쓰세요.

빈약한 페르소나를 만났을 때 어떻게 할지는 정하고 가시는 편이 좋습니다. 온보딩은 단계마다 데이터가
따로 쌓이는 구조라 **실제 운영에서도 일부 차원만 채워진 유저가 나올 수 있습니다.** 특정 차원이
없을 때 프롬프트를 어떻게 구성할지는 AI 쪽에서 정해두셔야 합니다.

### 3-2. `summary` 키가 API 문서에 빠져 있습니다

[internal-api-for-ai_v1.md](../api-spec/internal-api-for-ai_v1.md) 는 `personaElements` 의 키가 10종이라고
적고 있지만, **실제로는 `summary` 가 추가되어 11종입니다.** 그 문서가 낡았습니다.

| 키 | 설명 |
| --- | --- |
| `summary` | 유저를 한 문장으로 요약한 문자열. 항상 1개 |

예: `"친구들 약속을 먼저 챙기고, 고민이 많은 밤엔 혼자 오래 걷는 사람"`

나머지 10종은 기존 문서 그대로입니다. `personaElements` 는 **값이 있는 차원만 키로 포함**되므로
`elements.get("summary", [])` 로 접근하는 규칙도 그대로 적용됩니다.

### 3-3. 일부 시드 계정에는 실제 기기가 붙어 있습니다

`userId` **1, 6, 16** 에는 기기가 등록돼 있습니다. 프론트·QA 가 테스트 계정으로 로그인해 둔 것입니다.

이 유저들에게 `relationships` 를 `rapport ≥ 70` 으로 보내면 **채팅방이 열리고 실제 푸시 알림이
나갑니다.** `rapport ≥ 30` 으로 지인→친구 전환이 일어날 때도 마찬가지입니다. 임계값을 넘나드는
실험은 기기가 없는 다른 시드 유저(2~5, 7~15, 17~20)로 하시는 편이 조용합니다.

푸시가 나가도 데이터가 망가지지는 않으니 실수로 보내셨다고 큰일 나는 건 아닙니다. 다만 사람이
알림을 받고 무슨 일인지 물어보게 되므로 미리 알려드립니다.

### 3-4. 시드 유저에게는 이미 과거 시뮬레이션 데이터가 있습니다

이전 연동 테스트로 장면 204건, 관계 77건이 쌓여 있습니다. 깨끗한 상태에서 시작하고 싶으시면
말씀해 주세요. 백엔드에서 지워드립니다.

같은 `(userId, date)` 로 다시 POST 하면 그 날짜분이 통째로 교체되므로(기존 문서 4-1), **과거
데이터가 있다고 해서 새 요청이 실패하지는 않습니다.**

### 3-5. prod 에는 시드 유저가 없습니다

시더는 stage 와 local 에서만 동작합니다. prod 는 실제 가입자만 존재하므로, prod 에서 `userId`
1~20 을 기대하고 짠 코드는 동작하지 않습니다. **userId 를 하드코딩하지 마세요.**

## 4. 페르소나가 바뀌는 시점

시드 페르소나는 한 번 만들어지면 그대로 유지되지만, **설문 문항이 개정되면 전부 다시 만듭니다.**
문항이 바뀌면 기존 답변 문장이 더 이상 유효하지 않기 때문입니다.

실제로 2026-08-25 에 설문을 v2 로 교체하면서 20명 전원의 페르소나를 재생성했습니다. 설문 8개
차원의 문장이 전부 바뀌었고 관심사도 함께 바뀌었습니다. `detail` 과 `summary` 는 그대로입니다.

바뀔 때는 미리 공유드립니다. 다만 대비는 간단합니다.

**페르소나를 캐싱하지 말고 배치마다 조회하세요.** 기존 문서 4-5 에서 탈퇴 감지를 위해 이미 요구하는
사항이라, 그대로 지키시면 설문 개정도 자동으로 따라옵니다. 캐싱하면 개정 후에도 옛 문장으로
시뮬레이션이 돌아갑니다.

페르소나 문장 자체는 **시뮬레이션에서 바로 행동으로 옮길 수 있는 서술**로 통일되어 있습니다.
`"~을 선호함"` 같은 선호 서술이 아니라 `"공강 시간에는 도서관에 혼자 머문다"` 처럼 현재형 행동
서술이라, 프롬프트에 그대로 넣어 행동 판단 근거로 쓰시면 됩니다.

## 5. 로컬에서 같은 20명을 쓸 수 있나

가능합니다. 백엔드를 `local` 프로필로 띄우면 같은 시더가 돌고, **같은 20명이 같은 설문 응답으로
생성됩니다.** 유저별 고정 시드 난수라 환경이 달라도 결과가 같습니다.

`detail` 과 `summary` 는 미리 준비된 문장을 인덱스로 나눠 가지므로 항상 동일합니다. 반면 설문
응답과 `interest` 는 **설문 문항 수가 바뀌면 함께 바뀝니다.** 로컬과 stage 의 백엔드 버전이 다르면
두 환경의 페르소나가 어긋날 수 있으니, 비교 검증을 하실 거면 버전을 맞춰주세요.

일은 백엔드 쪽에서 처리합니다. 필요하시면 요청해 주세요.
